# Flash Filesystem

The SN110's persistent storage is a Minix v1 filesystem on ~3 MB of Intel flash
memory. Understanding the flash layout is important for recovery, firmware
updates, and avoiding bricking the device.

## Flash Chip

| Parameter | Value |
|-----------|-------|
| **Chip** | Intel TE28F320 |
| **Size** | 4 MB |
| **Bus width** | 16-bit |
| **Interface** | CFI (Common Flash Interface) |
| **Base address** | 0x00000000 (memory-mapped) |

## Flash Layout

| Block | Device | Purpose |
|-------|--------|---------|
| blk0 | `/dev/blk0` | Bootloader (rom.bin, <64 KB) |
| blk1 | `/dev/blk1` | Unknown |
| blk2 | `/dev/blk2` | Unknown |
| blk3 | `/dev/blk3` | Backup firmware image |
| blk4 | `/dev/blk4` | Unknown |
| blk5 | `/dev/blk5` | Main firmware image |
| blk6 | `/dev/blk6` | Unknown |

The Minix root filesystem is mounted from `/dev/root`, which maps to the
decompressed application image.

## Boot Process

1. Bootloader initializes NS7520 hardware
2. Validates application image via **32-bit CRC on the compressed image blob**
3. If CRC passes: decompress into RAM, mount Minix filesystem, boot kernel
4. If CRC fails: enter BOOTP/TFTP recovery loop

!!! warning "CRC validates the blob, not the filesystem"
    The bootloader's CRC covers the raw compressed image, not the files within
    it. A corrupted Minix filesystem will NOT trigger BOOTP recovery -- the
    kernel boots but panics on mount, entering a 3-second reboot loop.

## Minix Filesystem

| Parameter | Value |
|-----------|-------|
| **Type** | Minix v1 |
| **Magic** | 0x138F (little-endian) |
| **Max filename** | 14 characters (v1) or 30 (v2) |
| **Journaling** | None |

### Key Directories

```
/
  bin/          System utilities (sh, cat, ls, etc.)
  usr/bin/      User binaries (lxnetdmx, sn110lcd, dmxtst, nodecfg, etc.)
  etc/          Configuration files
    220node.cfg   Node configuration
    ifup-eth0     Network initialization script
  tmp/          RAM disk (lost on reboot -- safe for testing)
  dev/          Device files (dmx0, dmx1, lcd0, blk0-6, etc.)
  var/run/      PID files
```

### Important Files

| File | Purpose |
|------|---------|
| `/etc/220node.cfg` | Node configuration (IP, hostname, protocol, ports) |
| `/etc/ifup-eth0` | Network setup script (generated by config system) |
| `/usr/bin/lxnetdmx` | Factory DMX daemon (replaced by sn110dmx) |
| `/usr/bin/sn110lcd` | Factory LCD utility |
| `/usr/bin/nodecfg` | Strand config tool (reads/writes 220node.cfg to flash) |
| `/usr/bin/flashsw.sh` | Firmware update script (validates .chk, erases, writes) |
| `/var/run/lxnetdmx.pid` | PID file for the DMX daemon |

## Firmware Update (.chk Format)

Strand firmware updates use `.chk` files with this format:

```
Offset    Size     Content
0x0000    4        Checksum (32-bit little-endian)
0x0004    4092     Zero padding
0x1000    varies   Payload (compressed kernel + Minix filesystem)
```

The checksum algorithm: `(sum of all 32-bit LE words in payload + 9) mod 2^32`

The factory update process (`flashsw.sh`):

1. `nodecfg checksum` validates the .chk file
2. `eflash` erases the application flash sectors
3. `wflash` writes the payload to flash
4. `vflash` verifies the write
5. Reboot

## Safe Flash Write Practices

!!! danger "Writing to flash can brick the device"
    Always keep a backup of the original firmware. Test new binaries from
    `/tmp/` (RAM disk) before writing to flash.

### Safe Testing (RAM disk)

```bash
# Upload to /tmp/ -- lost on reboot, no risk to flash
curl -s -T build/sn110dmx.bflt ftp://192.168.2.231/tmp/sn110dmx
```

### Persistent Installation (Flash)

```bash
# Upload to flash -- survives reboots, overwrites existing file
curl -s -T build/sn110dmx.bflt ftp://192.168.2.231/usr/bin/sn110dmx
```

### Config Save Safety

The firmware uses **atomic write-to-tmp-then-rename** for config saves:

1. Write new config to `/tmp/220node.cfg.tmp`
2. `rename()` to `/etc/220node.cfg`

This prevents partial writes from corrupting the filesystem if the device
loses power during a save.

## Analysis Tool

The project includes `tools/analyze_flash.py` for analyzing flash dumps:

```bash
python3 tools/analyze_flash.py scan dump/sn110_full_flash.bin
python3 tools/analyze_flash.py diagnose dump/sn110_full_flash.bin
python3 tools/analyze_flash.py extract dump/sn110_full_flash.bin output_dir/
```
